1. What Module 2 Is

Your AI firewall (Module 1) stops bad traffic in real time — it blocks injections, redacts sensitive data, routes models safely, and logs every decision. Module 2 is where your security team lives after that. It turns those enforcement decisions into something a human team can act on: dashboards, risk scores, threat indicators, and formal incident cases.

Think of it this way: Module 1 is the guard at the door. Module 2 is the security operations center watching the cameras, reviewing who keeps knocking, and deciding when to lock someone out entirely.

Four questions Module 2 answers:
  1. Are attacks or misuse going up right now?
  2. Which API keys, models, tools, or data paths are highest risk?
  3. Which cases need immediate attention?
  4. What containment action should we take — disable a key, sync a new threat rule, escalate a case?

Everything on Module 2 screens comes from real enforcement telemetry produced by your gateway. When you run the demo app or built-in simulators, those requests flow through the same firewall and appear on these screens within seconds.

M2.1 SOC Command Center (Dashboard)

In Plain Language

When a SOC manager opens their shift, they start here. The Dashboard is your single pane of glass for AI security posture. It shows how much traffic passed through the gateway, how much was blocked or redacted, which lanes (chat, RAG, vector databases, MCP tools) are under pressure, and what is happening live right now.

Use case: A security lead logs in Monday morning and needs to answer: "Did anything bad happen over the weekend, and where should my team focus first?" They open the Dashboard, scan the top numbers, check which lane cards are red, glance at the live ticker, and drill into UEBA, Model/RAG, or MCP pages for detail.
Objective: Give leadership and analysts a fast, trustworthy snapshot of gateway health across all AI traffic types — without requiring them to dig through logs.

M2.2 API Key Behavior Analytics (UEBA)

In Plain Language

Every application connecting to your AI gateway uses an API key. UEBA watches how each key behaves over time. A key that normally sends 10 polite questions per hour suddenly sending 500 injection attempts is a compromise signal — even if each individual request was blocked.

Use case: An analyst sees repeated blocks from the same integration key. They open UEBA, find that key, review its behavior profile, and decide: "This looks like a compromised service account — disable the key and activate a kill switch."
Objective: Move from "something was blocked" to "this identity is risky and needs containment."

High Behavioral Risk KeysKeys scoring in the High risk band — your priority review list.

M2.3 Model & RAG Health

In Plain Language

Model Exposure answers: "Which LLM models are under the most attack or policy friction?" RAG & Retrieval answers: "Where in the document-Q&A pipeline are we losing control?" Two tabs because chat abuse and RAG abuse are different problems.

Use case: A platform owner sees elevated blocks on one model but not another — they adjust routing policy. Separately, RAG retriever blocks spike on one vector collection — they investigate poisoned documents or wrong ACLs.
Objective: Help teams prioritize which models and which RAG stages need policy attention.

M2.4 MCP & Context Risk

In Plain Language

Modern AI agents call tools — CRM lookups, SQL, tickets, files. MCP is how those tools connect. This page shows which tools and servers trigger security enforcement when agents try to use them.

Use case: Security wants to know: "Are agents sending dangerous SQL in tool arguments? Are tool responses leaking secrets back into the model?" They open MCP Risk after live tool calls and see which tools hit policy.
Objective: Visibility into agent tool-call risk — a blind spot in traditional API security.

Top KPI Cards

KPIWhat It Means
MCP EventsEvery tool call the firewall evaluated.
Blocked CallsTool calls completely stopped (dangerous SQL, path traversal, etc.).
Redacted CallsAllowed only after sensitive values were masked.
Unique ToolsDistinct tool names — sudden jumps may mean unexplored tools.
Policy Hit Rate% of MCP events ending in block or redaction.

Tool Activity vs Policy Hits (Grouped Bar)

Per tool: blue = total calls, amber = policy hits. High volume + low hits = noisy but safe. Few calls + many hits = priority to restrict.

Inbound vs Outbound Scans

  • Inbound — scans tool arguments before execution. High hit rate = bad inputs.
  • Outbound — scans tool responses before they reach the model. High hit rate = secrets in tool output.
  • Unknown — missing direction metadata; should stay near zero.

M2.5 Threat Intelligence Ops

In Plain Language

Analysts maintain a library of known-bad patterns — jailbreak phrases, malicious IPs, attack fingerprints. Add, edit, and sync indicators to the live gateway, then measure whether they catch traffic.

Important: The IOC table is your configuration library. KPIs and charts are live enforcement results. Adding an indicator does nothing until you click Sync to Gateway.

Use case: A researcher discovers a new jailbreak phrase. They add it as an IOC with Auto-Block, sync to gateway, and see IOC Matches rise when attackers use that phrase.
Objective: Close the loop between threat research and live gateway enforcement — with measurable effectiveness.

M2.6 Incidents & Forensics

In Plain Language

A blocked request is a log line. A security incident is a formal case your team works until the threat is understood and closed. Incidents open automatically when alert rules or anomaly detection decide something is serious enough to track.

Use case: Overnight, repeated high-severity blocks from one API key create an incident. The morning analyst filters Active + High, opens the case, reviews timeline and evidence, escalates to IR, and disables the key in UEBA.
Objective: End-to-end case management with audit trail — trackable, assignable, and defensible for compliance.

Closing Narrative for Clients

Your applications connect through our gateway — production chatbots, RAG knowledge bases, or the demo app. Module 1 enforces policy on every request. Module 2 gives your security team the operational layer:

  • Dashboard — morning posture
  • UEBA — when a specific API key looks suspicious
  • Model & RAG Health — which models or document pipelines are under attack
  • MCP Risk — when agents and tools are involved
  • Threat Intel — publish and measure new attack patterns
  • Incidents — formal tracking and closure

Every number, chart, and table comes from the same enforcement telemetry your firewall produces in production. When you run a block in the demo app, you will see it on the Dashboard within seconds, in UEBA under that API key, and potentially as an incident if alert rules say it is serious enough.

Module 1 protects. Module 2 lets you prove it, prioritize it, and respond to it.
