# Task 5.0 — how many synchronous Redis publishes per request, actually

**Tag `[M]`** · Docker `aimeshperf`, non-streaming, 5 requests, subscriber attached to
`logs:stream` inside the Redis container, commit `57fd7e10`

## Measured

| | per request |
|---|---:|
| log lines reaching **stdout** | 4.8 |
| records **published to Redis** (`logs:stream`) | **7.0** |

Breakdown as shipped, over 5 requests: 15 INFO, 11 WARNING, 9 DEBUG = 35 records.

## Correction to the plan

`docs/plans/2026-08-27-task-tracker.md` G4.5 says the request path performs
"**~17** synchronous `PUBLISH` per request". On this tree it is **7.0**. The plan's
figure is 2.4× high.

The stdout count (4.8) and the published count (7.0) differ because they are separate
handlers with separate levels — so counting `docker logs` would have **undercounted** the
thing that matters. The number that costs latency is the published one, since
`RedisLogPublisher.emit` calls `client.publish` inline on the calling thread.

## What this right-sizes

7 blocking Redis round trips per request, each on the event loop for an async handler,
each with `socket_timeout=1.0`. On a warm local Redis a round trip is a fraction of a
millisecond, so the *direct* cost is small — but the failure mode is not the mean. A
stalled Redis blocks the loop for up to 1 second **per record**, and under concurrency
every blocked publish serialises unrelated requests. That is the shape of the capacity
baseline's collapsing tail at 38% CPU.

Still a hypothesis. The discriminating experiment is stated in
`.kiro/specs/log-shipping-off-request-path/requirements.md`: re-run the capacity sweep
after task 2 (thread-per-regex, already fixed). If p99 collapses, thread churn was the
cause and this is a smaller separate win; if it does not, this becomes the live
explanation and the capacity baseline's stated hypothesis was wrong.

## Note on the measurement itself

The first attempt counted `docker logs` lines and got 4.8/request. That would have
under-reported the quantity of interest by 31%, because stdout is not the shipper. The
figure above comes from subscribing to the actual channel.
