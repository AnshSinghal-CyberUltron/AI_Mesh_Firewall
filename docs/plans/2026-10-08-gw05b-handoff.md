# GW05b handoff — what GW06 and deployment must do

GW05b closes R2-03 (SP1, SP2) and the gateway-side half of R2-04. Eight phases, all committed on
`suraj-revamp`, gates green: 538 offline / 591 with real Postgres + Valkey, 19 drills, 14 negative
controls biting, mypy `--strict` clean, import-linter 2 kept / 0 broken.

Evidence: `docs/plans/evidence/2026-10-08-gw05b/`. Plan and reasoning:
`docs/plans/2026-10-07-gw05b-state-freshness-and-ha-rehydration.md`.

This document exists because the card finishes with four things **implemented, tested and not
called**. That is not an oversight and it is not deferral of the hard part — it is a layering
fact: they need a process start-up path and an HTTP surface, and `gateway_v2/edge/` is still eight
stub files of three to five lines each.

A handoff document alone would not be enough. GW05c left `require_bounded_client` uncalled with a
docstring explaining exactly where it belonged, and an entire card went past without anyone
wiring it. Prose does not fail a build. So `tests/gates/test_lgw05b_handoff.py` pins the surface
and carries a tripwire that fails the moment `edge/` stops being stubs, with instructions.

## 1. GW06: four things to wire

### 1.1 `/readyz` must call `state_ready`

```python
from gateway_v2.runtime.state_stamp import state_ready

ready, why = state_ready(view)        # view: StampView | None
# 200 when ready; 503 with `why` in the body when not.
```

The runbook requires `/readyz` to be 503 while state is unverified, and L05b-6 is measured
through it. The predicate lives in `runtime` on purpose: a second definition written next to the
HTTP handler is how that requirement quietly stops being true.

It is keyed on freshness **alone**, not on the last round's per-kind outcome. A single failed
round is a blip and the kinds age out on their own; treating it as un-readiness would flap a
worker in and out of the load balancer on every store hiccup, which costs more availability than
it buys. A kind that stays broken stops the stamp — the re-hydrator withholds it — and that is
what surfaces here.

`state_ready(None)` returns `(True, None)`, so a deployment that has not yet built a `StampView`
can still start.

### 1.2 The start-up path must call `require_bounded_client`

```python
from gateway_v2.runtime.store_valkey import require_bounded_client

require_bounded_client(client, below_s=knobs.store_timeout_ceiling_s)
```

A paused or partitioned store does not refuse connections — it accepts them and never answers.
Without a per-operation timeout a refresh round simply never returns, so the snapshot never ages,
`state()` never reports `STALE`, and the fail-closed window the whole outage posture rests on
silently does not exist.

The ceiling is derived, not restated: `StateKnobs.store_timeout_ceiling_s` is half the refresh
period. C36's measured cost of getting this relationship wrong was a background store timeout
**equal** to the staleness ceiling, which produced fleet-wide fail-closed on every half-open
failover.

### 1.3 The request path must render `domain.posture`

| Kind | Condition | Code | Status |
|---|---|---|---|
| `ks` | `state()` is `STALE` | `kill_switch_unavailable` | 503 + `Retry-After` |
| `key` | `resolve` raises `StoreDataUnavailable` | `shared_state_unavailable` | 503 + `Retry-After` |
| `plan` | lookup returns `PlanUnavailable` | `plan_unavailable` | 503 + `Retry-After` |
| `budget` | *no producer yet* | `budget_unavailable` | 503 |

`Retry-After` comes from `gap_retry_after_s(rehydrate_period_ms=..., refresh_ms=...)` — one
re-hydrator period plus one gateway refresh, floored at 1 s. The floor matters as much as the
sum: R2-08 measured sheds carrying 6–11 ms of retry-after, which the OpenAI SDK retries so fast
that the retries become the load.

Three rules that are easy to get wrong:

- **`plan_unavailable`, never `plan_unknown_tenant`.** An unverified plan kind means we do not
  *know* whether the tenant exists; a 403 claims we do. C36 records RC2 answering "complete
  onboarding" and wedging live tenants at 403 for ever after a flush.
- **`shared_state_unavailable` is 503, never 401.** The key may be perfectly valid; what is in
  doubt is the state we would check it against.
- **Budget is narrower than the others.** A budget-kind failure spends the remaining lease and
  then refuses only quota. Treating it as global would turn a counter problem into an outage
  (R2-09). `admit/quota.py` is still a GW19 stub, so the code is named without a producer rather
  than wired speculatively.

The vocabulary is in `domain/posture.py` rather than `admit/posture.py` where RC2 kept it,
because `plan` sits *below* `admit` in the layer contract and needs the same codes. It is codes
only — no status, no message, no `ErrorSpec` — since `HTTPException` and `JSONResponse` are gated
out of those layers and `edge` owns rendering.

### 1.4 The loops must use the cadence hooks

```python
# gateway worker
reports = await sync.drain_all()
await asyncio.sleep(sync.next_delay_s(reports, period_s=knobs.refresh_period_ms / 1000))

# re-hydrator
summary = rehydrator.round_once(deep=knobs.is_deep_round(round_number))
```

`next_delay_s` returns 100 ms instead of the full period while the store answers but no usable
stamp has arrived — that is, while the process is not serving anything, so the extra polling costs
nothing anyone is waiting on. It bounds a new process's extra start-up at one re-hydrator round
plus 100 ms. Once fresh it returns the normal period, so the steady state R2-02 was measured in is
untouched. A process that could not reach the store at all waits the full period: hammering an
unreachable store is how a partition becomes a thundering herd.

`is_deep_round` makes round 1 shallow deliberately. The deep pass is O(records); charging start-up
for it would add the whole estate to the time before the first stamp, which is exactly the latency
a new process is already waiting on.

### 1.5 Config: GW06 owns the loader

`StateKnobs` validates every relationship on construction and is pure — no env reading. The names
the plan proposed, for whoever writes the loader:

| Env | Default | Knob |
|---|---|---|
| `AMF_STATE_FRESH_MS` | 5000 (`FRESH_MS`) | `fresh_ms` |
| `AMF_STATE_PG_GRACE_MS` | 16000 (`PG_GRACE_MS`) | `pg_grace_ms` |
| `AMF_REHYDRATE_PERIOD_MS` | 1000 | `rehydrate_period_ms` |
| `AMF_STATE_REFRESH_MS` | 500 | `refresh_period_ms` |
| `AMF_REHYDRATE_DEEP_EVERY` | 60 | `deep_every` |
| `AMF_REHYDRATOR_ID` | `hostname:pid` | `Rehydrator(name=...)` |

`StateKnobs.warnings` returns the lines a start-up path must log. It is non-empty when freshness
is disabled (`fresh_ms=0` reinstates R2-03) or the ride-through is off (a routine Cloud SQL
failover will then fail the fleet closed). Log them at WARNING; a break-glass that is silent is
not a break-glass.

**`FRESH_MS` and `PG_GRACE_MS` are owner-locked** in `domain/locks.py`. Consume them; do not
re-decide them. Note that the rc3 reference patch used 3000 for the freshness bound while the
locked value is 5000, so the patch's measured figures (2.04–2.97 s to global 503, ≈7.4 s on a 10 s
Postgres freeze) will be roughly 2 s longer here. Do not quote the patch's numbers as ours.

## 2. Deployment: four rules, one of them learned the hard way

These are specifications, not Terraform. The existing `infra/terraform/` is AWS and the v3 target
is GCP (GCE MIG, Cloud SQL, Memorystore), so writing manifests now would be inventing
infrastructure for a lane that has not been approved.

1. **≥ 2 re-hydrators in ≥ 2 zones.** One is a single point of global non-enforcement: when it
   stops, nothing compares the store with Postgres, and the whole fleet fails closed at
   `FRESH_MS`. Running two is already safe — publishes are WATCH-guarded, budget repairs are
   compare-and-set, a stamp is never replaced by an older one, and the live stack drives 50
   interleaved rounds from two re-hydrators with offset clocks asserting `verified_at` stays
   monotonic.

2. **No idle-stop policy may target a re-hydrator instance.** This is the round-2 ledger incident
   written as a rule: at 09:06Z an idle watchdog stopped `rv-r2state-cp-1`, which happened to host
   the only re-hydrator. R2-24 mandates an idle watchdog on every validation environment, so the
   watchdog's **exclusion list must name the re-hydrator instances explicitly**. An exclusion that
   relies on the instances looking busy will not hold: an O(1) round is nearly idle by design.

3. **`REHYDRATOR_ID` must be distinct per instance** (default `hostname:pid` already is). It
   travels in the stamp's `by` field, and it is how an operator knows which re-hydrator last
   verified.

4. **Re-hydrator maintenance windows must not overlap each other**, and neither may overlap Cloud
   SQL or Memorystore maintenance (R2-13, E2-08).

Cost note for the owner: two small control-plane VMs. The round is O(1) per kind since GW05c, so
these do not need to be large; the deep pass is the only O(records) work and it runs off the
critical path on a 60-round cadence.

## 3. Alarms

`deploy/observability/gw05b-state-freshness-alerts.yml` ships the rules in the established
Prometheus format. It is **deliberately not in `prometheus-scrape.example.yml`'s `rule_files`**:
the rules read the `amf_state_*` family, which only `gateway_v2` exports, and nothing serves
`/metrics` there yet. Wiring them is part of 1.1's work.

The severity convention is worth stating, because it inverts what you might expect. A gateway
that loses freshness **fails closed by design** — it is not serving bad data, it is refusing to
serve, with 503 and a `Retry-After`. So the page-worthy condition is the *cause* (nothing is
stamping) and the *symptom* is a warning that confirms the fail-closed path engaged.

Two rules need control-plane counters that do not exist yet, and both are named in R2-04:

- **`ok_publish_pending` older than one re-hydrator period** is the direct SP2 detector. A write
  that is durable-but-unpublished is invisible to every gateway by construction — that *is* the
  defect — so only the control plane can see it. Needs
  `amf_state_publish_pending_oldest_seconds`; the fallback query shape is the oldest
  `amf_state_log` row whose published flag is false.
- **`stamp_withheld`** counts rounds that could not verify every kind.

`StateClockSkew` deserves a note: `amf_state_stamp_age_seconds` is deliberately **not clamped at
zero**. A negative age means the gateway's clock and the re-hydrator's have drifted apart, and
skew in that direction *extends* the exposure window. Clamping would hide exactly the condition
the design cannot defend against.

## 5. What is not proven, and what it needs

| Test | Blocked on |
|---|---|
| L05b-1 | a real replica promotion. Drills substitute a partial restore and a rolled-back manifest — same class, not the same event. |
| L05b-2 | mechanism drilled; "every request 503" needs `edge/` (§1.1, §1.3). |
| L05b-3 | drilled locally (< 5 s). The reference figure of 0.54–0.79 s is Cloud SQL's. |
| L05b-4 | Cloud SQL failover at 60% load. The *shape* is drilled with a paused container. |
| L05b-5 | Memorystore maintenance cannot be triggered, and Valkey offers no manual failover at all (R2-13). |
| L05b-6 | drilled per process; "global" needs a fleet. |

Every measured bound in the evidence uses an **injected clock**. The fault is real — a stopped
database, a paused store, a held row lock — but the waiting is not, and no latency is claimed
anywhere.

The lane GW05b needs is materially cheaper than GW05c's: one gateway VM with a few workers, Cloud
SQL with a failover replica, Memorystore Valkey, two small re-hydrator VMs, one loadgen. **No L4
GPU and no 25k-tenant estate.** If only one lane gets funded, this card's gates should go first —
cheaper to clear, and they cover a CRITICAL correctness defect rather than a performance one.

## 6. Risks carried forward

- **Clock dependence (accepted).** Freshness compares the gateway's wall clock to the
  re-hydrator's. The `abs()` guard refuses a stamp from further ahead than the bound, so a badly
  skewed re-hydrator cannot pin the fleet fresh for ever, and `StateClockSkew` alarms on the
  gauge. NTP on both tiers is a deployment precondition. *Owner question: is NTP-dependent
  freshness acceptable as the v3 mechanism, or should a later card add a round-trip challenge?*
  The reference implementation accepted it.
- **`PG_GRACE_MS` margin is thin.** 16 s against a measured 15.5 s loaded Cloud SQL gap is 3%
  headroom. A test pins the relationship rather than retuning a locked constant. If L05b-4 fails
  on that margin, it is evidence for the owner.
- **A Postgres hang between connect and first statement.** `connect_timeout` covers connect,
  `statement_timeout` a hung query, `tcp_user_timeout` a dead peer. The sliver between is
  uncovered, inherited from the reference patch which also did not close it. Bounded consequence:
  the round fails, the stamp is withheld, the grace applies.
- **The "verified" predicate is weaker than rc3's.** A GW05b stamp attests versions, positions and
  counts — not contents. rc3 compared a whole-set digest, which GW05c deleted and now gates
  against, because tying freshness to an O(records) round makes global availability a function of
  tenant count. Content divergence under matching counts is covered by the occasional deep pass
  and by record-level signatures on the read path. This is a deliberate weakening and should be
  reviewed as one.
- **Stamp age at 50k records is unmeasured.** The rc3 README flagged it. GW05c's O(1) diagnose
  removes the main driver, but first-start catch-up does still scale (0.09 / 0.93 / 2.40 s at 1k /
  10k / 25k), and the deep pass reads every record of a kind.
- **`fresh_ms=0` is a real escape hatch.** It disables the 503 and reinstates R2-03. Loud at
  start-up via `StateKnobs.warnings`, visible as `amf_state_stamp_fresh`, never a default.
  *Owner question: should it be removed before v3 sign-off?*
