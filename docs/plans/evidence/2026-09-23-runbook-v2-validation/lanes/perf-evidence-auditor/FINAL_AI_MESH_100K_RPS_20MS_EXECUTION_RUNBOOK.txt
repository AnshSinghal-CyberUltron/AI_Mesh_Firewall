Release target
Build a stateless, organization-controlled AI gateway that uses no platform-owned external AI APIs for enforcement, remains OpenAI-SDK and SSE compatible, sustains 100,000 fully evaluated gateway requests per second at fleet level on the signed qualification workload, and adds less than 20 ms p99 firewall overhead relative to the same provider path without AI Mesh.

2. Non-negotiable measurement definitions
Firewall overhead is measured against a direct-to-provider control using the same producer, network path class, payload, token schedule and client. Provider time is never guessed from TTFT subtraction.
For streaming, publish three values: p99 first-content added delay, p99 maximum per-request release lag caused by AI Mesh, and p99 completion overhead. A whole-response-withholding policy is a separate mode and cannot inherit the low-latency streaming claim.
100k goodput excludes gateway 5xx, incomplete SSE streams, skipped selected guards, schedule drops, load-generator misses and scan-only responses. Intentional 4xx policy blocks are reported separately and never counted as successful allowed completions.
The 100k result is fleet-level. Single-node and RPS/vCPU efficiency are separately measured and published.
A customer SaaS BYOK endpoint is not required to sustain 100k completions/s. The gateway must prove 100k with a controlled/dedicated producer; real-provider capacity is reported separately.

A valid empty organization policy is different from missing/stale/unavailable policy state.
Policy transformations precede scanners that consume the transformed bytes. Do not parallelize dependent stages merely to win latency.
Redaction success is determined from actual provider/client bytes, not a dashboard action label.
No selected detector may be reported as executed when it was skipped, degraded or unavailable.

No synchronous audit/logging network call on the ordinary request critical path.
No runtime model download, TensorRT engine compilation or fallback-to-CPU after readiness succeeds.

Objective
Preserve low-latency SSE behavior while applying selected output controls without leaks, duplication, deadlocks or hidden buffering.
Why this task exists
SSE is a product contract, not only a transport. Guard buffering, proxy buffering, boundary-spanning secrets, provider errors and client disconnects all affect correctness and perceived latency.
Implementation steps
Define two explicit modes: LOW_LATENCY_STREAM (bounded lookbehind/holdback) and STRICT_WHOLE_RESPONSE (no release until final decision).
For low-latency mode, use bounded trailing context sufficient for supported deterministic patterns; never hold the whole response accidentally.
Run lightweight per-chunk deterministic scans only when required; run completion-only semantic classifiers once at DONE unless the policy specifically requires incremental semantics.
Disable proxy buffering and compression behaviors that delay text/event-stream. Configure keepalive, idle timeouts and graceful drain for long streams.
Propagate backpressure; stop reading/generating aggressively if the client is slow/disconnected.
Define post-header security failure framing: valid OpenAI-compatible SSE error event + terminal behavior; do not attempt to change HTTP status after streaming begins.
Verification / test cases
TTFT test: producer emits first chunk at 50 ms; AI Mesh low-latency mode adds <20 ms p99 first-content delay under the signed load.
Gap test: 16 chunks spaced 5 ms remain ordered and are not coalesced into a single final burst.
Boundary test: email/API key split across 2-4 chunks is never released raw when REDACT is enabled.
Tool-call test: function argument deltas split across chunks remain valid and reconstruct to provider-equivalent JSON.
Disconnect test: client closes after chunk 3; upstream and guard activity terminate within the configured cancellation bound.
Slow-client test: memory remains bounded; queue depth hits a defined threshold and backpressure/load shedding activates.
Provider reset test: stream emits a parseable error and terminates; no fake success [DONE] without error context.
Strict-mode test: zero bytes are delivered before final output decision.
Failure / stop conditions
First content waits until DONE in low-latency mode.
Chunks duplicate/reorder/drop.
Cross-boundary secret leaks.
Memory grows with response length or slow client.
Proxy buffers SSE.
Output block occurs only after unsafe bytes were already released while UI claims “nothing delivered”.
Success criteria
OpenAI SDK streaming matrix passes.
p99 release-lag metric exists and stays within the signed P1 limit.
No boundary leak in held-out streaming corpus.
Strict and low-latency modes are visibly distinct in config and telemetry.
Exit evidence required
Raw sanitized SSE transcripts.
Chunk timing trace.
Proxy config test.
Disconnect/backpressure metrics.

8. External reference principles used in this runbook
TrueFoundry Gateway Plane Architecture: documents stateless gateway pods, in-memory authentication/authorization/rate/load-balancing decisions, asynchronous logging/config propagation, readiness dependent on configuration, and horizontal CPU scaling. It currently reports about 350 RPS on 1 vCPU and roughly +7 to +12 ms in its published gateway benchmark depending tracing. Treat these as vendor/reference results, not an apples-to-apples security benchmark.
Envoy Gateway: documents both local and global rate limiting. Local rate limiting is lightweight and per instance; global rate limiting coordinates across the fleet through an external rate-limit service/datastore. AI Mesh uses the same layered design principle but must measure its own consistency/latency trade-off.
OpenAI Python SDK: streaming responses use Server-Sent Events; both sync and async clients iterate streamed events. The runbook therefore treats SSE parsing, event order, terminal behavior, cancellation and tool-call deltas as compatibility gates rather than optional UI tests.
