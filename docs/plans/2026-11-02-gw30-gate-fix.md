# GW30 gate failures — root cause and fix (plan)

Status date: 2 November 2026, branch `suraj-revamp`.

## Symptom

The full offline suite fails two gates, both on `gateway_v2/dispatch/vector_live_transports.py`
(landed by the GW30 commits `e4455c92`..`d111fde1`):

- `tests/gates/test_empty_tree_passes.py::test_shipped_tree_within_size_limits` — module is 1309
  lines (max 800).
- `tests/gates/test_check_tenant_scale.py::test_the_shipped_data_plane_is_clean` — `smembers`
  (line 402), `scan_iter` (458), `keys` (775).

## Root causes (verified in code)

| Hit | Cause | Real defect? |
|---|---|---|
| size | Eight transports in one module | Structural only |
| `keys` (Weaviate `list_collections`) | `client.collections.list_all().keys()` is a Python dict | No — gate false positive |
| `smembers` (Redis `query`) | The live gate ran plain `redis:7.4-alpine` (no vector index), so `query` reads every member id and issues one `HGET` per record: N+1 round trips per query, O(collection) | **Yes** — per-request cost grows with collection size |
| `scan_iter` (Redis `list_collections`) | SCAN over the whole keyspace for `gw30:index:*` | **Yes** — O(keyspace) |

Found while tracing, not reported by any gate:

- **Data loss on `create_collection`.** Six transports delete existing data before creating:
  Qdrant `recreate_collection`, Weaviate `collections.delete`, Elasticsearch and OpenSearch
  `indices.delete`, Chroma `delete_collection`, Mongo `drop()`. Only pgvector (`IF NOT EXISTS`)
  and Redis are non-destructive. Wired to a customer store, a create on an existing collection
  would wipe it.
- **Wrong Redis.** The live harness pointed the Redis transport at `127.0.0.1:6379`, the main
  stack's shared state Redis, so the gate wrote `gw30:*` keys into it and scanned its keyspace.

## Review outcome (supersedes "Fix" below where they disagree)

One contradictory reviewer, every point re-checked in code:

- **Accepted, changes the fix:** GW30 requirement 2.9 says a create on an existing collection
  SHALL return a declared failure code, so `vector_ok` + `status="exists"` was wrong. Added
  `posture.COLLECTION_EXISTS`; each transport calls the store's atomic create and maps the store's
  own "already exists" error to it (no check-then-create race).
- **Accepted, recorded as open GW30 findings (not fixed here; not what the gates flagged):**
  1. Mongo `query` is `find({})` + in-client cosine, O(collection); the gate does not know `find`.
  2. `filters=True` is declared for every connector but no transport reads `req.filter`, and
     upserts drop metadata, so a filtered query silently returns unfiltered results (R3.6).
  3. Partial upserts possible on pgvector and Elasticsearch (one statement per record, R2.4).
  4. Delete counts reported as `len(ids)` on Qdrant and Chroma, +1 per id on Weaviate.
  5. Elasticsearch/OpenSearch delete swallows every per-document exception, so a connection
     failure is `vector_ok` count 0 (R6.3).
  6. Weaviate `batch.dynamic()` does not raise on failed objects; upsert reports the full count.
  7. Name sanitisation maps `a-b` and `a_b` to one collection; Elasticsearch also lowercases.
  8. Mongo opens a `MongoClient` per operation and never closes it (ResourceWarning in the run).
  9. The store SDKs are synchronous; `asyncio.wait_for` cannot interrupt them, so the R6.4
     timeout is really the SDKs' own 5 s.

## Fix (original plan)

1. **Split** the module into a package `dispatch/vector_transports/` (`_common`, `pgvector`,
   `redis`, `qdrant`, `weaviate`, `elastic` (ES + OpenSearch), `chroma`, `mongo`; `__init__`
   re-exports). Delete `vector_live_transports.py`; the two harness scripts are its only importers
   and are updated.
2. **Redis → server-side KNN (RediSearch).** `create_collection` = `FT.CREATE` over a hash prefix
   with a FLOAT32 `VECTOR` field (COSINE); `query` = one `FT.SEARCH ... KNN` call; `upsert` stores
   FLOAT32 bytes; `delete` deletes the hashes; `list_collections` = `FT._LIST` filtered to the
   transport's prefix. No whole-collection read remains. A Redis without the search module fails
   closed (`VectorTransportError` → `provider_unreachable`), never brute force.
3. **Weaviate** lists collections by iterating the dict (no `.keys()` call).
4. **Non-destructive create everywhere.** An existing collection returns `vector_ok` with
   `status="exists"` and is not touched. Dimension mismatch on an existing collection is not
   detected at create (surfaces on upsert as a store error) — recorded, not hidden.
5. **Store stack.** Add `redis/redis-stack-server` to `docker-compose.gw30-stores.yml` on its own
   port; the harness uses it and never the shared state Redis.
6. **Tests.** Offline: a static test that no transport's `create_collection` calls a destructive
   API; the gates. Live: re-run L30-1/2/3 with Redis included, plus a new L30-1b — create a
   collection, upsert, create again, the records are still there — on every live store.
