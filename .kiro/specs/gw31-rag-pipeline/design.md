# Design Document

## Overview

GW31 replaces the two `_placeholder` 501 handlers for `POST /v1/rag/query` and `POST /v1/vector/query` with a served RAG and vector surface. It also re-registers the retired collection, document, vector-config and admin routes, adds asynchronous ingest, puts `project` on `Principal`, and compiles the six RAG settings into the plan. It WIRES the shipped GW30 adapter (`dispatch/vector_adapter.py`, `VectorRegistry`, the connectors). It does not change them. It consumes GW26 stage scoping (`PlanResolver(stage=...)`) and changes no resolver semantics.

A `POST /v1/rag/query` request runs in this order, and every refusal is a declared value-code rendered by `edge/errors.py`:

1. Identity (`identity_of`), plan lookup (`lookup_plan(..., Surface.RAG)`), `rag_enabled` gate.
2. Admission (`AdmissionController`) and budget (`QuotaComponent`), exactly as MCP does in `McpRoute._admit_and_charge`.
3. **Query stage**: bound check, canonicalise, scan with stage `query`, embed the query.
4. **Retriever stage**: `Vector_Adapter.query` through `VectorRegistry.select(store_id)`, then per-chunk scan with stage `retriever`, then bind and cap.
5. **Ranker stage**: relevance, threshold, distance anomaly, trust re-rank, near-duplicate cap, `rag_max_documents`, scan with stage `ranker`.
6. **Generator stage**: context binding re-check, redaction (byte-verified), canary frame, optional local-model grounding through `GuardBackend` (Tier-2), optional injected `Answerer`, output scan with stage `generator`, canary check.
7. Audit record and per-request exports on every exit, including refusals.

### Technology stack (locked on approval)

Python 3.12, raw ASGI (no framework), the existing `ResourceContract`, `PlanResolver`, `scan_deltas`, `apply_decision`, `AdmissionController`, `QuotaComponent`, `PerRequestExports`, `emit_chat_audit`. Tests: pytest with seeded `random.Random` properties (house idiom, no `hypothesis`), `fakeredis` where a store is needed, `Stub_Vector_Connector` for the adapter, local Chroma for the L31-3 local half. **No new third-party dependency** (Req 20.8). No `llm_judge`, no Titan, no remote platform AI.

## Value types (all `@dataclass(frozen=True, slots=True)`)

In `domain/rag.py`:

```python
@dataclass(frozen=True, slots=True)
class RagSettings:
    rag_enabled: bool = True
    vector_db_isolation: str = "project"          # closed set {"project", "org"}
    rag_max_documents: int | None = None          # None = ResourceContract ceiling
    rag_relevance_threshold: float | None = None  # None = ResourceContract default
    rag_redaction_enabled: bool = True
    rag_tier2_enabled: bool = True

class TrustLevel(IntEnum):  # higher = more trusted
    UNTRUSTED = 0; LOW = 1; MEDIUM = 2; HIGH = 3

@dataclass(frozen=True, slots=True)
class Chunk:
    chunk_id: str
    text: str
    vector: tuple[float, ...]
    org_id: str
    project: str
    source: str
    trust: TrustLevel

@dataclass(frozen=True, slots=True)
class ScoredChunk:
    chunk: Chunk
    relevance: float          # [0.0, 1.0]
    decision: Decision | None # retriever-stage decision (REDACT/FLAG carried to the generator)

@dataclass(frozen=True, slots=True)
class StageNote:
    stage: str                # "query" | "retriever" | "ranker" | "generator"
    action: str               # disposition value or "skip"/"refuse"
    reason: str               # declared code or ""
    dropped: int              # chunks removed by this stage
    rule_ids: tuple[str, ...] # deciding rules, for the audit trace
```

Settings stay a plain value on the plan. The two `None` defaults are deliberate: the numeric defaults are capacity-position values and live only in the contract. `plan/rag_settings.py::effective_settings` resolves them into `EffectiveRag` (frozen: the six settings with every `None` filled and `top_k` precomputed).

`dispatch/rag_*` value types (frozen, slotted): `Retrieval(code: str, records: tuple[VectorRecord, ...] | None)`, `RankOutcome(chunks: tuple[ScoredChunk, ...], dropped_blocked: int, dropped_anomalous: int, dropped_duplicate: int, dropped_threshold: int, dropped_unscorable: int)`, `ContextFrame(text: str, canary_digest: str)` (the frame never stores the canary in clear; see below), `IngestJob(job_id, org_id, project, collection, state, code, stored, total)`, `RagDeps` (edge). Every mapping a value holds is a `MappingProxyType`; tuples and frozensets elsewhere.

## Key decisions

**D-1. Stage logic is split by dependency, not by name.** Scanning needs the detector and the resolver, and `dispatch` sits below both. So `edge/rag_stages.py` owns the four stage entry points and calls scanners, and `dispatch/rag_*.py` owns the pure steps they call (retrieval, ranking, context binding). This is the same split chat uses (`edge/input_enforcement.py` scans, `dispatch/transform.py` transforms). It also keeps the ranker property-testable with no detector at all.

**D-2. Stage scope is bound by one edge helper.** `rag_stages.resolver_at(route, plan, phase, surface, stage)` calls `resolver_for(...)` and, when the result is a `PlanResolver`, returns `dataclasses.replace(resolver, stage=stage)`. **Fail-closed binding (round 4 F-2):** if `resolver_for(...)` returns anything that is not a `PlanResolver`, `resolver_at` raises `RagInternalError`, rendered `rag_internal_error` (500) with zero adapter calls; it never returns an unscoped resolver, because with `stage=None` `_stage_admits` skips every stage-scoped rule (a silent fail-open of admin intent). At dev build time `dev_rag.build_dev_rag` asserts `deps["phase_resolvers"] is not None` and refuses to build `RagDeps` otherwise (round 5 F-1: the chat route does not exist yet there). The request-time check in `resolver_at` is the real guard. Test: a chat route without `phase_resolvers` refuses the RAG request (500 `rag_internal_error`, zero adapter calls). Every scan in the four stages and the vector routes goes through it, so no stage can forget the name. The vector routes pass `Surface.VECTOR`. Ingest passes `stage=None` (an ingest is not a pipeline stage, so stage-scoped rules do not fire there; Decision D-8). Req 6.1 to 6.4 follow from `resolve/conflict.py::_stage_admits`: a rule with `pipeline_stage = "query"` fires only when the helper passes `"query"`, and an empty-stage rule fires in all four. The surface filter in the same function gives the chat-only versus retrieval-only behaviour (L26-1).

**D-3. Namespaces are built once, are injective over the `(org, project, collection)` triple, and are case-stable (review passes 1 and 3).** The wire string is an encode-each-segment-then-join of LOWERCASE-only segments, so it is injective over triples, immune to case folding on any connector, and bounded by a length derived from a per-connector table.

- `Namespace` is a frozen, slotted value `(org_id, project, collection)` in `domain/rag.py`. `build_namespace(org_id, project, collection, isolation) -> Namespace` is the only constructor path (Req 9.5, as amended by C-5). With `vector_db_isolation = "org"` the project segment is the fixed string `default`.
- `validate_segment(value, max_len)` accepts only ASCII **lowercase** `[a-z0-9_-]`, non-empty, `len <= max_len`, applied to **all three** segments including `org_id` (which `admit/identity.py::_text` only checks as non-empty). **Uppercase is refused, never folded** (`rag_namespace_refused`, zero adapter calls). The same lowercase rule applies to `project` in `principal_of` (D-4), so an uppercase project key is `project_invalid`. This resolves the case-fold collision (`AB` vs `ab` on Elastic/Postgres): no two accepted triples differ only in case, and the wire name is already lowercase, so every fold is the identity. The dev profile is unaffected: `DEFAULT_DEV_ORG_ID = "dev-org"` (`edge/dev_profile.py:105`) is lowercase and in charset, and `tests/edge/test_gw31_routes.py` includes a test that builds the dev `RagDeps` and Principal from the default dev profile and asserts the first `/v1/rag/query` is not refused with `rag_namespace_refused` (a custom `AMF_DEV_ORG_ID` with uppercase is refused, and the dev-profile docstring says so). Real-world impact: an org id that contains uppercase (for example an unnormalised UUID) is refused on RAG routes with `rag_namespace_refused`; the operator note says to issue lowercase org ids. This is the conservative fail-closed choice for an unattended run.
- `encode_segment(seg) = seg.replace("_", "_u").replace("-", "_d")`. The encoded alphabet is `[a-z0-9_]`, every `_` followed by exactly one of `u`/`d`.
- `wire_collection(ns) = "o" + enc(org) + "_s" + enc(project) + "_s" + enc(collection)`. `_s` cannot occur inside an encoded segment, so the separator is unambiguous. The string contains only `[a-z0-9_]`, so `safe_name` is the identity on it and `wire == wire.lower()`. It starts with `o` and ends with an alphanumeric or `u`/`d` letter (an encoded segment never ends in a bare `_`), satisfying Chroma's alphanumeric start/end rule.
- `parse_wire(name) -> Namespace | None` tokenises left to right (`_u`, `_d`, `_s`), returns `None` for any other shape. `list_collections` keeps a name only if `parse_wire(name)` yields a Namespace whose `(org_id, project)` equals the effective `(org, project)` from `build_namespace` (F-7).
- **Per-connector naming table and the derived length (review pass 3, finding 3).** The adapter-visible name is transformed by each transport before it reaches the store. Verified by reading each `*_transport.py` in this worktree:

| Connector | Transformed name | Prefix chars | Folds case | Length limit that binds |
| --- | --- | --- | --- | --- |
| chroma | `"gw30_" + safe_name(c)` | 5 | no | 3 to 63 total, alphanumeric start and end |
| pgvector | table `gw30_` + `safe_name(c)` | 5 | yes (unquoted identifier) | 63 total (Postgres identifier) |
| elastic | `"gw30_" + safe_name(c).lower()` | 5 | yes (explicit) | 255 bytes |
| milvus | `"gw30_" + safe_name(c)` | 5 | no | 255 |
| mongo | `"gw30_" + safe_name(c)` | 5 | no | collection name well under 120 bytes |
| weaviate | `"Gw30_"` + folded alnum/underscore | 5 | first letter only | no practical limit below the others |
| redis | index `gw30idx:` + name, keys `gw30:` + name + `:` | 8 | no | no limit below the others |
| pinecone | namespace `safe_name(c)`, no prefix | 0 | no | no limit visible in the transport; the store's own namespace limit is UNVERIFIED here |
| qdrant | `c` unchanged, no prefix | 0 | no | none below 63 |

  **Assumption (F-9):** 58 assumes 63 is the strictest limit across connectors. The Pinecone namespace limit is not visible in the transport code and is not cited here; 58 is a conservative assumption, to be confirmed only by the deferred cloud-store run, and the constant's docstring says so. If Pinecone enforces a lower limit, the cloud run fails closed on a store error, not a leak.

  `RagBounds.wire_max_length = strictest_total_limit - longest_prefix = 63 - 5 = 58`. This number is a named constant in `runtime/resources_rag.py` whose docstring cites the table; it is derived, not guessed. (Redis's 8-character prefix has no binding limit, so it does not reduce the budget.) The per-segment RAW bounds are numeric named constants in `runtime/resources_rag.py`: `org_max_length = 36`, `project_max_length = 32`, `collection_max_length = 32`. They are upper limits per segment only; the binding check is the **encoded wire string** `<= wire_max_length (58)`. Arithmetic (F-4 fix): the fixed overhead is 5 characters (`o` plus two `_s`), and every `-` or `_` in a segment costs one extra encoded character. So the budget for the three encoded segments is 58 - 5 = 53. The worst case per segment is double its raw length (a segment of only `-`/`_`), so the three maxima can sum to 200 encoded characters; the global check, not the per-segment maxima, is what keeps the name within 58. A hyphenated 36-character UUID org id encodes to 40 characters (4 hyphens), leaving 53 - 40 = 13 characters for the encoded project and collection together: with the default project `default` (7) that is 6 characters for the collection. Documented consequence and operator note: hyphenated UUID org ids leave very short collection names; operators who need longer collection names should issue compact lowercase org ids (for example 32 hex characters, which encode to 32 and leave 21). Longer combinations are refused with `rag_namespace_refused`, never truncated. A test pins both numbers (UUID org + `default` + 6-character collection passes, 7 fails).
- **Transport-naming test.** `tests/dispatch/test_gw31_namespace.py` imports every shipped transport's naming function (`_name`, `_index`, `_table`, `_coll`, `_cls`, `_namespace`) and asserts, for 10,000 random in-bound triples, that the transformed name (a) is accepted unchanged (equals `prefix + wire` or `prefix + wire.lower()` with the lower case being identity), (b) has total length `<= 63` for the 63-limited connectors, and (c) is injective across the sample. A new connector's naming function must be added to the test's table (a coverage assertion enumerates `vector_transports/*_transport.py`).
- The only builder of a wire string is `wire_collection`. A source-grep test asserts no other module builds `"_s"` joins or calls `encode_segment`.
- Operator note: switching `vector_db_isolation` between `project` and `org` changes the namespace of existing data. Earlier collections become unreachable under the new setting (not leaked; switching back restores them).

**D-4. `project` on `Principal` (review finding 3).** One code: `project_invalid`. `principal_of` reads optional `project` from the signed record. Absent or JSON `null` gives `"default"`. A present value that is not a string, is empty after `strip()`, or has a character outside `[a-z0-9_-]` (uppercase included, see D-3) raises `ProjectInvalid`, a new exception in `admit/identity.py` that subclasses `StoreDataUnavailable` (so any catch site not yet updated still fails closed as a 503, never a rewritten project). `edge/identity_resolver` catches `ProjectInvalid` before `StoreDataUnavailable` and renders `project_invalid` (503, `service_unavailable`); `shared_state_unavailable` is not used for this case. `principal_of` gains an optional keyword `max_project_len: int | None = None`; the boot-time `fetch` closure injects `contract.rag_bounds().project_max_length`, and when it is given an over-long value also raises `ProjectInvalid`. Consequences, stated so the tester does not guess: (a) a key record with a malformed (charset) or, in a booted gateway, over-long project is refused with `project_invalid` on **every** route including chat, because the key record is malformed and nothing about it is trusted; (b) when the keyword is absent (unit tests, existing callers) the length is not checked in `principal_of`, and `edge/rag.py::_scope` re-checks it against the contract on RAG routes only, so the over-long key then authenticates on chat but is refused on RAG with `project_invalid`. Both layers enforce; the edge check gates RAG. Old tests stay green (Req 9.8). P11 covers charset and length, with and without the keyword.

Request-time resolution (`effective_settings(plan, contract)`) reads only `plan.rag` from the pinned snapshot the request holds. There is no mutable global (Req 16.3).

**D-6. The generator does not call a chat model by default.** The runbook says the v1 ranker and generator use no model, and Req 5 describes verification "before and after the model call" without naming a model. Conservative decision: `POST /v1/rag/query` returns the verified, redacted, bound context (and its trace). A `RagDeps.answerer: Answerer | None` seam (`async answer(frame_text, query) -> str | None`, defined in `dispatch/rag_context.py`) is optional. When injected, the answer is produced from the framed context and then runs through the same post-model checks. When `None`, the response has `"answer": null`. This is recorded as an assumption; adding a model call is a later card and needs no change to the checks.

**D-7. Canary.** `mint_canary(token_source)` takes an injected `Callable[[int], str]` (production passes `secrets.token_hex`) and a length from the contract. The canary is placed inside the framed context (`<<ctx:{canary}>> ... <</ctx:{canary}>>`) that is handed to the answerer and to the grounding check. The route never puts the frame in the response body. The response carries each chunk's redacted text, and `answer` when present. After generation, `canary_present(output_texts, canary)` checks every outgoing string (answer, every chunk text; the response carries no client metadata, D-13). A hit means the context leaked: the response is withheld with `rag_output_withheld`. **Stated limit (review pass 3, finding 6):** in GW31 the canary is placed in the frame that goes to the grounder and, when injected, the answerer. With `answerer = None` nothing consumes the frame except the grounder, so the check can fire only if a canary appears in outgoing text (for example a chunk whose stored text contains it, or a faulty injected answerer or grounder that echoes the frame). It is a tripwire for context-frame leakage, not a proof about model behaviour, and GW31 does not claim it covers model leakage. Tests: a chunk whose text contains the minted canary (via an injected `token_source` that returns a known value) is withheld with `rag_output_withheld`; a fake answerer that echoes the frame is withheld; with no answerer and clean chunks the check passes and `canary_hit` is false. The canary value is never logged, audited, or placed in an error body; the audit record carries only a boolean `canary_hit` (Req 17.3, P9). `ContextFrame` stores `sha256(canary)` hex, not the canary, so the frame value is safe to log in a test failure message.

**D-8. Ingest content is scanned with stage `None`.** Ingest is not one of the four query stages. Stage-scoped rules (`pipeline_stage` set) therefore do not fire on ingest, and empty-stage rules for `Surface.RAG` do. A BLOCK refuses with `rag_ingest_blocked` before 202. A REDACT stores the masked, byte-verified text. This is a documented conservative choice, not a gap: a poisoned document is still caught at retrieval by the `retriever` stage.

**D-9. "Durably queued" (requirements Clarification C-7).** In GW31 "durably queued" means **recorded in the injected `IngestJobStore`**; it does not mean survives process exit, which only a store-backed implementation (GW36) provides. Req 8.1 and the Async_Ingest glossary are read that way, and the evidence must state which store ran (in-memory or store-backed). The runtime has no job store outside Redis-style state, and GW36 owns boot wiring. `IngestJobStore` is a protocol with `put(job) -> bool`, `get`, `update` (`put` returns `False` or raises when the record was not durably accepted by that store). **No 202 without a successful `put`:** a `False` return or an exception from `put` refuses the request with `rag_unavailable` (503, ERROR rate-limited), nothing is queued, and no job id is returned. Test: a store whose `put` returns `False`, and one whose `put` raises, each yield 503 `rag_unavailable`, zero queue submissions and zero adapter calls; the in-process implementation is bounded (contract) and evicts oldest finished jobs only. 202 is returned after `put` succeeded and the job was enqueued. `RagDeps.ingest_store` accepts a store-backed implementation at GW36. The honest limit (an in-memory store loses accepted jobs on process exit, and `GET` then returns `rag_job_not_found`) is stated in the response docs and the evidence, never hidden. A lost job never reports `stored`.

**D-10. Stages cannot be switched off (requirements clarification, finding 11).** Req 2.7, 4.8, 5.8 allow a stage to be disabled by "an explicit valid plan setting", but the six settings contain no stage toggle. No such setting is invented, so the "disabled by setting" branch of those criteria is vacuous in GW31 and the tester should not look for a toggle. Recorded in the requirements clarifications appendix. All four stages always run. `rag_enabled = false` is the only whole-pipeline off switch, and `rag_tier2_enabled` and `rag_redaction_enabled` switch only the checks named in Req 14 and 15.

**D-11. Query embedding.** The query must become a vector before retrieval. `Embedder` is a protocol in `dispatch/rag_embedding.py`: `class Embedder(Protocol): dimension: int` (read-only property, a positive int, used by query step 5, ingest `create_collection` and admin create) and `async def embed(self, org_id: str, texts: tuple[str, ...]) -> tuple[tuple[float, ...], ...] | None`, `None` meaning unavailable. Wiring asserts `dimension >= 1`. The production embedder is a boot wiring concern (GW36); GW31 ships `DeterministicHashEmbedder` (feature hashing of lowercased word tokens into a contract-sized dimension, L2 normalised, no model, no network) for the dev profile and for tests so L31-3 can run locally. If `RagDeps.embedder` is `None` the query returns `rag_embedder_unavailable` (503) with zero adapter calls. `/v1/vector/query` takes the vector from the client body and needs no embedder.

## Request handling, stage by stage

### Route lifecycle (`edge/rag.py::RagRoute`)

`RagRoute` is a frozen dataclass holding `chat: ChatRoute` (identity, snapshot source, admission, quota, contract, detector, clock, audit, observer, exports) and `deps: RagDeps`. Each handler follows the MCP shape: a per-request `_Ctx` holding a `RequestHolds`, `try` run, `except _Refuse as stop`, `finally` `emit_chat_audit(..., route="rag", detail={"stage": ..., "code": ...})` then `ctx.holds.release(...)`. `_Refuse(code)` is the one control-flow exception, private to `edge/rag*.py`.

Order inside a handler: read body bounded by `contract.rag_bounds().body_bytes` (over: `rag_request_too_large`) then parse JSON (`rag_invalid_request`) then `identity_of` then `lookup_plan` (`PlanUnavailable` / `PlanUnknownTenant` both `plan_unavailable`) then `effective_settings` then `rag_enabled` gate (`rag_disabled`) then project re-check then `_admit_and_charge` (identical to MCP: `admission.admit`, `quota.evaluate`, cost from `estimate_request_tokens`) then the pipeline. Auth, admission and budget all precede the first adapter call (Req 1.7). Any exception that is not `_Refuse` is caught at the outermost `try` and rendered as the generic `scan_failure`-family refusal `rag_internal_error` (500, logged once at ERROR through the event log with the exception class name only, no message text, because messages can carry chunk text).

### Query stage (`rag_stages.run_query`)

Input: `query: object`. Steps, each fail-closed:

1. Bounds: not a `str`, empty after `strip()`, or `len(query.encode()) > bounds.query_bytes` gives `rag_query_invalid` before any scan or adapter call (Req 2.5).
2. **Raw-text scan; no separate canonicalisation step (finding 7).** Canonicalisation is internal to the deterministic detector: `detect/deterministic/detectors.py:154` calls `canonicalize(text, DEFAULT_BUDGET)` and maps spans back with `SpanMap.to_original`, so every `Finding` span is already in the coordinates of the text handed in. The route therefore passes the stripped-of-nothing original query text to `scan_deltas`; spans index the original text, `apply_decision` works on the original text, and no mapping is done in the route. The same holds for chunks and generator output.
3. `scan_deltas((("rag:query", text),), join_runs=(), detector=bind_surface(chat.input_detector, Surface.RAG), resolver=resolver_at(chat, plan, Phase.INPUT, Surface.RAG, "query"))`. `refuse_code` set gives `_Refuse(refuse_code)` (that is `scan_failure` or a policy-regex code). BLOCK gives `rag_query_blocked`. REDACT applies `apply_decision` and byte-verifies (raw span absent) or refuses `input_unmaskable`. Only the redacted text goes on (Req 2.4).
4. **Detector selection and surface binding (finding 7).** `rag_stages.detector_for(deps, effective)` returns `chat.input_detector` when `rag_tier2_enabled` else `deps.detector_tier1` (deterministic-only; GW09 stays on, Tier-2 skipped, Req 15.4). It then calls `bind_surface(detector, Surface.RAG)` (or `Surface.VECTOR` on vector routes). `bind_surface` (`edge/dev_components.py:340`) binds the surface **only** when the detector is a `DeterministicFindings`; any other callable is returned unchanged. Therefore the contract on both injected detectors is: each MUST be (or be built on) a `DeterministicFindings` so the surface binds, and a Tier-2 detector composes the deterministic one and adds semantic findings (the shipped dev/production composition). `RagDeps` construction asserts this at wiring time: if `bind_surface(d, Surface.RAG) is d` for a detector that is not a `DeterministicFindings`, the wiring raises (fail at start, not at request time), unless the detector is explicitly marked surface-agnostic by the composing wrapper. Test: a surface-`rag` customer condition fires under both `rag_tier2_enabled=True` and `False`, and a surface-`chat` condition fires under neither (P10 extension). Both detectors are injected, never built here.
5. Embed the redacted query. `None` or an exception gives `rag_embedder_unavailable`. The vector length must equal the collection dimension the embedder reports; mismatch gives `rag_embedder_unavailable` (never a padded vector).

A BLOCK or any refusal here returns before step "Retriever", so P1 (zero adapter and model calls) holds structurally: `retrieve` and the answerer are called only after `run_query` returns a `QueryOutcome`.

### Retriever stage (`rag_stages.run_retriever`, `dispatch/rag_retrieval.retrieve`)

1. `store = deps.store_id_of(org_id)` (injected `Callable[[str], str | None]`; `None` gives `store_not_configured`). `VectorRegistry.select(store)` returns an adapter or an `AdapterResult` miss. A miss propagates its code (Req 3.1: no other connector, no fallback).
2. Build `QueryRequest(org_id, store_id, collection=wire_collection(ns), vector, top_k=effective.top_k)` with `namespace=None` and `filter=None`. `top_k` is `min(effective max documents, contract.vector_max_result_count())` (Req 12.5).
3. `result = await adapter.query(req)`. Not `result.ok` propagates `result.code` unchanged. `result.ok` with `records == ()` is a successful empty retrieval and the pipeline continues with an empty context (Req 3.3). `result.ok` with `records is None` violates the GW30 invariant and gives `rag_retrieval_invalid` (fail closed).
4. **Resolve chunk content through the ChunkStore (D-13), not through record metadata.** Take only `record.id` from each returned `VectorRecord` (the shipped transports return empty metadata, and not every one returns a vector). Call `chunk_store.get_many(wire_collection, ids)` once. For each id with an entry, build `Chunk(chunk_id=id, text=entry.text, vector=entry.vector, org_id=principal.org_id, project=effective project, source=entry.source, trust=entry.trust)`. Org and project come from the Principal and the store key (which embeds both through the wire name), never from stored metadata. An id with **no entry** (a store miss, expired, never written through GW31, or written by another path) is excluded and counted as `dropped_unscorable`; a vector present in the adapter but absent from the ChunkStore therefore never reaches the model. The relevance vector is the `ChunkEntry.vector` written at ingest; `record.vector` is ignored, so the pipeline does not depend on any connector returning vectors. If the adapter returned at least one id and **every** returned id misses the ChunkStore, that is treated as a lost or foreign ChunkStore (a restart, another worker process, or ids written by another path), never as a true no-match: the request is refused with `rag_chunk_store_unavailable` (503), a rate-limited ERROR is logged with counts only, and no empty 200 is returned. A **partial** miss (some ids found) keeps the drop-and-count behaviour with the trace showing `dropped_unscorable = n`. An adapter result with zero records is still the successful empty retrieval of step 3, because there is nothing to miss. The all-miss rule is applied in `rag_stages.run_retriever` before the chunk scan, so it also covers `/v1/vector/query` (L31-1 path).
5. Scan every chunk: `scan_deltas((("rag:chunk", chunk.text),), ..., resolver=resolver_at(..., Phase.INPUT, Surface.RAG, "retriever"))`, one call per chunk. Phase is `INPUT` because retrieved content is untrusted input to the model. BLOCK excludes the chunk. A scan that cannot be computed excludes the chunk and records the failure (Req 3.5). REDACT and FLAG keep the chunk and carry the `Decision` in `ScoredChunk.decision`. The same detector runs for the chunk scan as for the query, so a poisoned chunk is detected on every path that reaches this function, including `/v1/vector/query` (L31-1).
6. The cap by `rag_max_documents` happens after scan and again after ranking (Req 12.2). Scan cost is bounded by `top_k`.

### Ranker stage (`rag_stages.run_ranker`, `dispatch/rag_ranker.py`)

All steps are pure and deterministic. Ties break by `(−relevance, −trust, chunk_id)`, never by arrival order or hash seed.

1. Relevance: `cos = cosine(query_vector, chunk.vector)`; `relevance = (cos + 1) / 2` clamped to `[0,1]`. **Mapping consequence (review F-6):** orthogonal vectors score about 0.5, so a configured threshold below 0.5 filters nothing that is merely unrelated, and the default `_RAG_DEFAULT_RELEVANCE` must be chosen with this mapping in mind (a value comfortably above 0.5). The constant's docstring records the mapping, the chosen value and its source; the runbook and v1 give no number (requirements assumption 3), so the value is a conservative documented choice, and a unit test in `test_gw31_rag_bounds.py` asserts the default is `> 0.5` and in `[0,1]`. Req 13.2 ("normalised relevance") is satisfied by this mapping. A non-finite value, a zero-norm vector, or a length mismatch drops the chunk (`dropped_unscorable`, Req 4.7).
2. Threshold: drop `relevance < threshold`. If all drop, the context is empty and the pipeline continues; the threshold is never lowered (Req 13.5).
3. Distance anomaly: over the surviving set, compute `distance = 1 − relevance`, median `m`, and `MAD`. Drop a chunk with `(distance − m) / (1.4826 × MAD) > bounds.anomaly_z` when `MAD > 0`; when `MAD == 0` and the set has at least `bounds.anomaly_min_set` members, drop chunks with `distance − m > bounds.anomaly_floor`. Smaller sets skip the step (a statistic over two points is not meaningful). MAD is a deterministic order statistic with no model (Req 4.2).
4. Near-duplicate cap: two chunks are near-duplicates when `cosine(a.vector, b.vector) ≥ bounds.duplicate_similarity` OR their normalised-text 5-shingle Jaccard is `≥ bounds.duplicate_jaccard`. Group by greedy single-link clustering in deterministic order (cluster key: best member by trust, relevance, `chunk_id`). Within each cluster order members highest trust first (then relevance, then `chunk_id`). **The cap is measured against the post-cap final context (round 4 F-3), not the pre-cap survivor count.** With `f = bounds.near_duplicate_fraction = 0.5`, a cluster keeps `kept_c ≤ max(1, floor(f × final_size))` where `final_size` is the size of the final context after capping, found as the fixed point: start with `kept_c = size_c` for all clusters and repeatedly lower any cluster with `kept_c > max(1, floor(f × Σ kept))` to that bound until nothing changes (clusters processed in deterministic key order; the iteration is monotone decreasing so it terminates in at most n rounds). Consequences: a context made of one cluster keeps exactly 1 chunk; a flood of 10 duplicates beside 2 other chunks keeps 2 of them (2 ≤ floor(0.5 × 4)); one source is never erased entirely. The excess is dropped lowest trust first (Req 4.4, L31-2). P4 and L31-2 measure share on this post-cap output.
5. Trust re-rank: sort by `(−trust, −relevance, chunk_id)` for chunks that cleared the threshold, then truncate to the cap on `rag_max_documents`. Because trust is the primary key, a lower-trust chunk never outranks an otherwise equal higher-trust one (P5).
6. **Ranker scan (stage `ranker`), per chunk (finding 6).** The unit is one chunk, exactly as at the retriever stage: one `scan_deltas((("rag:chunk", chunk.text),), join_runs=(), ..., resolver=resolver_at(..., Phase.INPUT, Surface.RAG, "ranker"))` per surviving chunk. There is no concatenation, no separator and no custom span mapping, because spans are relative to that chunk's own text, which is what the generator's `apply_decision(text, decision, 0)` expects. The ranker decision for a chunk is combined with its retriever decision by `rag_context.merge_decisions(retriever, ranker) -> Decision` (pure, in `dispatch`, domain types only): dispositions combine with `most_restrictive`; transformations of both are sorted by start, and overlapping or touching spans are coalesced into their union carrying the replacement of the earliest-starting one (ties: retriever first), so no raw byte of either finding survives and no overlap reaches `apply_decision`; `findings`/`per_finding` are concatenated with the ranker `finding_index` values offset by the retriever finding count; `deciding_rules` are unioned in order. Because the `Decision` invariant requires disposition == most restrictive per-finding, the merged object is built after the combination and always satisfies it. A ranker BLOCK **drops that chunk** (counted in `RankOutcome.dropped_blocked`, consistent with the retriever stage and Req 4), it does not refuse the request; an empty surviving context continues as an empty context. **Known limit, stated:** a secret split across two chunks is not detectable by any per-chunk scan; it is an input to the generator-stage output scan (stage `generator`) over the answer, and a per-chunk boundary-straddle test documents that the retriever and ranker stages do not claim to catch it (P2 extension: each chunk is scanned, and the split-secret fixture asserts the per-chunk behaviour and that nothing crashes or leaks a fully-formed secret).

### Generator stage (`rag_stages.run_generator`, `dispatch/rag_context.py`)

1. Context binding: every chunk's `(org, project)` must equal the request's `(org_id, effective project)`. A chunk that does not is removed (counted, never logged with text) (Req 5.2). The chunk's org and project come from the Principal and the ChunkStore key (D-13), so this check guards against a code path that supplies a Chunk built for a different request; it is a defensive second check, not the primary binding.
2. Redaction when `rag_redaction_enabled`: apply each chunk's carried `Decision` via `egress.output_guard.apply_decision`, then verify by bytes that no raw finding span survives in the produced text. An `apply_decision` `ValueError` (partial or overlapping span) or a surviving span withholds the response (`rag_output_withheld`, Req 5.7). When `rag_redaction_enabled` is false, REDACT decisions are recorded in the trace as `redact_not_applied` but not applied, and any BLOCK decision still refuses (Req 14.4); a BLOCK is never downgraded. **Step 6 uses this same gate** (see below).
3. Frame and canary (D-7).
4. Grounding when `rag_tier2_enabled`. Protocols (in `dispatch/rag_context.py`): `class Grounder(Protocol): async def check(self, frame_text: str, query: str) -> GroundingVerdict`, and `@dataclass(frozen=True, slots=True) class GroundingVerdict: code: str; score: float | None = None`, with the closed code set `{"ok", "unavailable"}` (any other code is treated as `unavailable`, fail closed). `Answerer` is likewise `async def answer(self, frame_text: str, query: str) -> str | None`. **Meaning in GW31: grounding is an availability and fail-closed gate only.** A verdict `ok` lets the response proceed; `unavailable`, `deps.grounder is None`, a raise, or a timeout under `contract.vector_operation_timeout_s()` withholds with `rag_grounding_unavailable` (Req 5.6). `score` is carried into the trace when present but never changes an outcome; hallucination scoring and any grounded/ungrounded label semantics are GW33. The production grounder will wrap the GW08 `GuardBackend.classify(windows, budget)` via the GW10 semantic detector (the seam `dispatch/authorized.py` documents) and map backend readiness to `ok`/`unavailable`; the GW31 test grounder returns `GroundingVerdict("ok", 1.0)` or `("unavailable", None)` as scripted. Tests therefore assert only the availability branches, never a score-driven block.
5. Answerer, if injected, runs after steps 1 to 4. Its exception or `None` gives `rag_answer_unavailable` (502); a context-only response is not substituted silently.
6. **Output scan (stage `generator`), fully specified (review F-2).**
   - **Function and detector.** `scan_deltas` (edge/input_enforcement.py) is not input-specific: its `detector` parameter is `Callable[[str], Sequence[Finding]]` and its `resolver` is an `OutputResolver` (verified in the code). Chat's `ErrorFrameScanner` is the same callable type (`edge/error_frame_scan.py:104`). So the generator scan reuses `scan_deltas` with `detector=detector_for(deps, effective)` bound to `Surface.RAG` (the identical detector the query and chunk scans used, so Tier-2 on/off applies uniformly) and `resolver=resolver_at(chat, plan, Phase.OUTPUT, Surface.RAG, "generator")`. **`RagDeps` gains no `output_detector`** and the chat output path is not touched or reused.
   - **Scan unit.** One `scan_deltas` call per outgoing string, in this order: the answer (when present), then each chunk's text as it will be sent (after step 2 redaction). No concatenation, so spans index each string's own text and `apply_decision(text, decision, 0)` applies directly.
   - **Purpose of rescanning chunks.** Chunks were scanned at `retriever` and `ranker` with `Phase.INPUT`. The generator scan uses `Phase.OUTPUT` and stage `generator`, so (a) output-phase and `generator`-stage customer rules fire on live requests (Req 6.5), and (b) it is the last gate over the exact bytes that leave the process, including bytes produced by step 2's redaction. It is not a second semantic opinion on the same stage.
   - **Redaction gate.** Same condition as step 2. `rag_redaction_enabled = true`: REDACT is applied with `apply_decision` and byte-verified (surviving span or `ValueError` gives `rag_output_withheld`). `rag_redaction_enabled = false`: REDACT is recorded as `redact_not_applied` and the string goes out unmodified, BLOCK still withholds (`rag_output_withheld`), so there is no conflict between steps 2 and 6 and no downgrade of BLOCK. A scan that raises or returns `refuse_code` withholds with `rag_output_withheld` (fail closed).
   - **Tests** (`tests/edge/test_gw31_generator_stage.py`, one per branch): output-phase `generator` rule fires on a chunk; stage-`query` rule does not fire here; redaction on + REDACT on the answer is masked and byte-verified; redaction off + REDACT on a chunk leaves it and records `redact_not_applied`; redaction off + BLOCK withholds; detector raising withholds; Tier-2 off uses `detector_tier1` for this scan.
7. Canary check over all outgoing strings (D-7).

Only after step 7 does `edge/rag.py` build the 200 JSON body: `{"request_id", "context": [{"id","text","source","trust","relevance"}], "answer": str|null, "trace": [StageNote...]}`. Chunk text is the only content field, and it is the redacted text. The trace carries counts, stage names and rule ids, never text.

### Vector routes

`POST /v1/vector/query` takes `{collection, vector, top_k?}`, and runs the Retriever scan and the Ranker steps (not the Query stage, there is no text) with `Surface.VECTOR`. The threshold, anomaly, trust and duplicate steps run on the vector response too (Req 7.5). `POST /v1/vector/upsert` takes `{collection, trust?, records:[{id,text,source?,metadata?}]}` and is **synchronous**: it reuses the ingest worker's per-batch function (`ensure collection (D-14) -> embed -> chunk_store.put_many -> adapter.upsert`, the same order as ingest, `dispatch/rag_ingest.py::write_batch`) run on the request, so the two paths cannot drift (F-3). Same rules as ingest: optional top-level `trust` (`untrusted|low|medium`, default `medium`, `low` for a record without `source`, never above `medium`); id charset and length (D-14); bounds `upsert_records_per_request` (= `ingest_documents_per_request`) and `ingest_document_bytes`/`chunk_text_bytes` per record and total body bytes (over gives `rag_ingest_too_large` 413); the content scan of D-8 with `Surface.VECTOR` (BLOCK gives `rag_ingest_blocked`, REDACT stores the masked text); embedder `None` or failure gives `rag_embedder_unavailable` (503) with zero adapter calls; the F-1 rollback rule applies unchanged (the shared function owns it); a ChunkStore refusal gives `vector_capacity_exceeded`. Success returns 200 `{stored: n}` only on an observed OK with matching count. **D-13. GW31-owned ChunkStore (review pass 3, finding 1, HIGH).** Option (a) of the review is chosen over amending GW30, because GW30 is shipped and the scope boundary is "wire, do not rebuild".

- `ChunkEntry` is frozen/slotted `(text: str, vector: tuple[float, ...], source: str, trust: TrustLevel)`. `ChunkStore` is a protocol in `dispatch/rag_chunks.py`: `async put_many(collection: str, entries: Mapping[str, ChunkEntry]) -> bool`, `async get_many(collection: str, ids: tuple[str, ...]) -> Mapping[str, ChunkEntry] | None` (`None` means the store is unavailable), `async delete_many(collection: str, ids: tuple[str, ...]) -> bool`. `collection` is always the encoded wire name, so org and project are part of the key and a cross-tenant read is structurally impossible: a caller can only ask for a wire name it built from its own Principal.
- `InMemoryChunkStore` holds a `dict` instance attribute (not module-level) behind its object, bounded by `RagBounds.chunk_store_entries` (derived from `ingest_queue_depth` and `ingest_documents_per_request`, in `runtime/resources_rag.py`) and `chunk_store_bytes`. When full it REFUSES the put (`False`), the ingest job fails with `vector_capacity_exceeded`, nothing is evicted silently (an eviction would silently remove the model-visible text of an indexed vector; refusing is the fail-closed choice). A durable implementation is GW36 and is a drop-in behind the protocol.
- **Ingest order (one order, stated once; round 4 F-5).** `dispatch/rag_ingest.py::write_batch` is the single implementation used by the async worker AND `/v1/vector/upsert`: (1) ensure the collection (D-14), (2) embed, (3) `chunk_store.put_many`, (4) `adapter.upsert`. Failures at (1) or (2) write nothing, so the ChunkStore is untouched (test: N failed ensure attempts leave the ChunkStore count at 0). `put_many` is an idempotent overwrite by `(collection, id)` and charges capacity per distinct key, so a retry of the same ids consumes no extra capacity. If (3) fails (`False`) the job is `failed` with `vector_capacity_exceeded` and the adapter is not called. **Rollback rule (F-1, F-6).** After (4), the batch's entries are deleted via `delete_many` ONLY on a definite wrote-nothing failure: the adapter returned a declared non-OK code in the frozen set `WROTE_NOTHING_CODES = {unsupported_operation, credential_unavailable, credential_scope_mismatch, org_identity_invalid, vector_capacity_unset}` (all are rejected before any provider call; these names exist in `domain/posture.py`). `vector_capacity_exceeded`, `provider_unreachable`, `credential_leak_withheld`, any unknown code, a raise, a timeout and a count mismatch are AMBIGUOUS and the entries are KEPT, because the adapter may have written some or all vectors and a vector without an entry is dropped at retrieval and can turn a query into `rag_chunk_store_unavailable`. **Reclaim of kept entries:** a retry of the same ids overwrites them without extra capacity, and `DELETE /v1/rag/documents` by ids calls `delete_many`; nothing else reclaims them, which is an accepted bounded leak (the store refuses puts when full with `vector_capacity_exceeded`, and a restart clears it). The job is marked `failed` with the code in all cases. An entry with no vector is harmless (reads are by returned id); a vector with no entry is not. `stored` is set only when (3) returned `True` and (4) was OK with the matching count (P8). P8/P16 add a case: a scripted adapter that writes then raises (and one that times out, and one that returns a short count) followed by a query returns the documents (or at worst a partial result), never a 503 from orphans.
- **Delete.** `DELETE /v1/rag/documents` and the ids form of `DELETE /v1/rag/collections` call `adapter.delete` first and then `chunk_store.delete_many`; a ChunkStore failure after an OK adapter delete is logged at WARNING (the vector is gone, so the leftover entry is unreachable) and the response is still success only if the adapter delete succeeded.
- **ChunkStore unavailable or lost at query time** gives the declared refusal `rag_chunk_store_unavailable` (503), never an empty success. Two triggers: (1) `get_many` returns `None` or raises; (2) the adapter returned at least one id and **all** ids are absent from the ChunkStore (Retriever step 4). A partial miss drops and counts only the missing ids. Test (`test_gw31_retrieval.py` and `test_gw31_routes.py`): all-miss gives 503 with zero scans, zero answerer calls and a `rag_chunk_store_unavailable` audit code, partial miss gives 200 with the found chunks and `dropped_unscorable = n`, zero-record adapter result gives 200 empty.
- **Single-process limit, stated.** `InMemoryChunkStore` and the in-memory job store live in one process. With several workers or after a restart, data ingested in another process is invisible, and queries then fail closed with `rag_chunk_store_unavailable` (all-miss) instead of returning an empty answer. The dev profile must therefore run one worker (documented in the dev-profile docstring and the evidence). A shared durable ChunkStore is GW36.
- **No `rag_connector_unsupported` check (review F-3, option a).** The wiring-time check and the code are **deleted**; nothing named `rag_connector_unsupported` exists. Reason: GW31 relies only on the id of each returned record, and reading every shipped transport's query path shows the id is the original id for all nine: Chroma `str(ids[i])`, Pinecone `str(m["id"])`, Milvus `str(h.get("id", ...))`, Mongo `str(doc["_id"])`, Redis `fields["rid"]`, Elastic `_source["rid"]`, Qdrant `payload["rid"]` (point ids go through `as_point_id` but the original id is stored in the payload), Weaviate `properties["rid"]` (same), pgvector `str(row[0])` (the table stores `record.id`). Milvus returns an empty vector, which D-13 already tolerates. The proof is a test, not a runtime check: `tests/dispatch/test_gw31_retrieval.py` runs an upsert-then-query id round trip through every transport that has an in-process fake client, and a **coverage assertion** enumerates `vector_transports/*_transport.py` and fails if a transport is neither in the round-trip table nor in an explicit `EXPECTED_SKIP` set with a one-line reason each. Today `test_gw30_transport_safety.py` has fakes for Weaviate, Redis, Elastic and similar; any transport without a fake (to be confirmed by the implementer when writing the table) goes in `EXPECTED_SKIP` with the source-line evidence above, and the id-source line is additionally pinned by a source-text test so a change to it fails the suite. If a future transport cannot return the original id, the failing coverage test forces a GW30 follow-up before it can be used for RAG.
- **Wire-through test.** `tests/dispatch/test_gw31_retrieval.py` includes a retrieval test over the Stub connector configured as the real connectors behave (query returns records with `metadata = {}` and, in a second parametrisation, `vector = ()`): the context is still fully populated via the ChunkStore, which is the L31-3 local-half contract. A second test checks a returned id that is absent from the ChunkStore is dropped and counted, never forwarded. A third parametrised test runs ingest then query through each shipped transport class with its in-process fake client where one exists (Chroma, Pinecone, Elastic, pgvector fakes already used by GW30 tests), asserting the returned ids round-trip to the ids that were upserted (some transports map ids through `as_point_id`; the original id is kept in the payload). Coverage is enforced by the assertion in the "No `rag_connector_unsupported` check" bullet above; there is no runtime connector check.

**D-14. Collection lifecycle and list normalisation (review F-3, F-4, F-8).**

- **Ingest ensures the collection.** Chroma `upsert` calls `get_collection` (no create) and pgvector needs the table from `create_collection`, so an ingest to a never-created collection would fail. Decision: before the first `upsert` of a job the worker calls `adapter.create_collection(CreateRequest(collection=wire, dimension=embedder.dimension, metric="cosine"))` and treats `VECTOR_OK` and `collection_exists` as success; any other code fails the job with that code and `upsert` is not called. This also makes Pinecone work (its create always answers `collection_exists`). Ingest therefore does not require a prior `POST /v1/rag/collections`. `POST /v1/rag/collections` on an existing collection returns 409 (`collection_exists`); on Pinecone that is the expected result. Test sequence (L31-3 local half, `test_gw31_ingest.py` and `test_gw31_routes.py`): ingest to a never-created Chroma collection (fake or local), job reaches `stored`, then `/v1/rag/query` returns the document; a fake whose create returns `collection_exists` still stores; a fake whose create returns another code gives `failed` with that code and zero upserts.
- **`listed_name(raw: str) -> str | None`** in `dispatch/rag_retrieval.py`: strips a leading `Gw30_` or `gw30_` case-insensitively (Weaviate's `list_collections` returns `Gw30_o...` unstripped), lowercases nothing else, and returns the name only if it then matches the lowercase wire shape `[a-z0-9_]+`; otherwise `None` (dropped). Names already stripped by their connector (Chroma, Milvus, Mongo, Elastic, pgvector, Redis) pass through unchanged. `GET /v1/rag/collections` applies `listed_name` then `parse_wire`. Test: `test_gw31_namespace.py` / `test_gw31_retrieval.py` assert `create -> list` returns the same wire name for every transport that has a fake client, and a Weaviate-shaped `Gw30_` list result is kept. **Documented limit:** Pinecone lists only namespaces that currently hold vectors, so a freshly created empty collection does not appear in the list until it holds a record. This is recorded in the evidence and the Pinecone case sits in the test's `EXPECTED_SKIP` with that reason.
- **Id and `top_k` validation (`RagBounds`).** `id_max_length` (named constant), `ids_per_request` (derived: `ingest_documents_per_request`), and the id charset: printable ASCII `0x21..0x7E` (no spaces or control characters). Applies to ingest `documents[].id`, upsert `records[].id` and delete `ids`; a violation, an over-count, or a non-string id gives `rag_invalid_request` before anything is queued, embedded or sent. An ingest document without an id gets a gateway-minted id from the injected `token_source`. `top_k` on `/v1/vector/query` must be an `int` (not `bool`) `>= 1`, otherwise `rag_invalid_request`; the effective value is `min(top_k, effective max documents, vector_max_result_count())`.

Every handler: authenticates, loads the plan, enforces `rag_enabled`, builds the namespace through `build_namespace`, makes zero adapter calls on a refusal, and checks the request's collection name with `validate_segment` first (`rag_namespace_refused`, Req 9.6). There is no request field that selects an org or a project; the Principal is the only source.

### Async ingest (`dispatch/rag_ingest.py`, `edge/rag_ingest.py`)

`POST /v1/rag/ingest` body: `{collection, documents:[{id?, text, metadata?, source?}]}`. Accept path:

1. Auth, plan, `rag_enabled`, project check, admission and budget (as above).
2. Bounds from `contract.rag_bounds()`: documents per request, bytes per document, total bytes. Over gives `rag_ingest_too_large` (413) before queueing.
3. Scan each document text (D-8). BLOCK gives `rag_ingest_blocked` (400, whole request refused, nothing queued). REDACT replaces text with the verified masked text.
4. Build `IngestJob(state="accepted")`, `store.put(job)` (a `False` return or raise gives `rag_unavailable` 503 and nothing is queued, D-9), then `queue.submit(job, payload)`. `submit` is non-blocking: queue full (depth from contract) gives `rag_ingest_overload` (503) with `Retry-After` from `posture.gap_retry_after_s` (at least `MIN_RETRY_AFTER_S`), and the job is removed from the store, so nothing is dropped silently.
5. Return 202 `{"job_id", "state":"accepted"}`.

Background worker: `IngestQueue` is created with an injected `spawn: Callable[[Coroutine], object]` (production: `asyncio.create_task` wrapper), `clock`, `token_source`, the `Embedder`, and the `VectorRegistry`. A bounded semaphore (concurrency from contract) limits running jobs. A job: embed each document (failure marks `failed`/`rag_embedder_unavailable`), run `write_batch` (ensure collection D-14, embed, ChunkStore put D-13, then `adapter.upsert(UpsertRequest(collection=wire_collection(ns), records=...))` with records carrying id and vector only (metadata is not relied on) for whichever connector the org has (not Pinecone only; Req 8.2), then record the outcome. `result.ok` with `count == len(records)` AND a successful ChunkStore put gives `stored`. Any other code, a count mismatch, a raise, or a timeout gives `failed` with the declared code (a raised exception maps to `provider_unreachable`). `stored` is set only on an observed OK (P8). A job writes only to the namespace it was created with; the namespace is computed once at accept time from the Principal and carried in the job, never recomputed from request data in the worker (Req 8.8). `GET /v1/rag/ingest/{job_id}` (prefix route) returns the job only if `job.org_id == principal.org_id and job.project == effective_project` (the job record stores the effective project from `build_namespace` at accept time, so under `vector_db_isolation = "org"` it is `default`; F-7); otherwise `rag_job_not_found` (404), so an id from another tenant is indistinguishable from a missing one.

Trust and reserved metadata (finding 5). The ingest body gains an optional top-level `trust` field: one of `"untrusted"`, `"low"`, `"medium"`; any other value (including `"high"`, a non-string, a number) is rejected with `rag_invalid_request`. Default `medium`, but `low` when the document has no `source`. A caller can lower trust, never raise it above `MEDIUM`; raising needs an operator role not modelled in GW31, so a poisoned document cannot be laundered upward. **Reserved keys:** `ingest` and `/v1/vector/upsert` reject any client `metadata` key starting `_rag_` with `rag_invalid_request` before anything is queued or embedded, and client metadata is not persisted anywhere in GW31 (the adapter drops it and the ChunkStore does not keep it). Trust, source, org and project are supplied by the gateway only: org and project from the job's accept-time Namespace, trust and source from the validated body fields, written into `ChunkEntry` and the ChunkStore key. `rag_context.stamp_metadata` is removed from the design; there is no client-influenced metadata path to forge. Forgery test (P14 extension): random `_rag_*` keys and values in documents are refused at accept and never alter the stored org, project or trust.

### Scan cost bound (F-5)

`_RAG_MAX_DOCUMENTS` is a named constant in `runtime/resources_rag.py`, value 20 (v1 parity is recorded in its docstring); the effective ceiling is `min(20, vector_max_result_count())`. Worst-case detector calls per RAG request: 3 chunk-scan loops (retriever, ranker, generator) x 20 chunks = 60 chunk scans, plus the query scan and one answer scan (62). The ranker's greedy near-duplicate clustering is O(n^2) pairs over n <= 20 (at most 190 cosine plus shingle-Jaccard comparisons). Decision: the three chunk-scan loops run through `ScanExecutor.run` (`edge/executor.py`, off the event loop, the same executor chat uses; the stage receives it from `chat.executor`, the one `ScanExecutor` that `build_app` creates at `app.py:293` and passes to the chat route as `executor=scan_executor`; RAG never builds a second pool), and the ranker runs inline because its bounded pure-CPU cost (190 pair tests over chunks of at most `chunk_text_bytes`) is below the loop-lag budget; the L31 evidence records the measured loop lag with 20 chunks at `chunk_text_bytes`. If `ScanExecutor` is saturated or raises, the request is refused fail-closed with the declared scan-unavailable code, never scanned inline as a fallback.

## Fail-closed behaviour at every boundary

| Boundary | Failure | Result |
| --- | --- | --- |
| Body read, parse, field types | over bound, bad JSON, wrong type | refuse, zero downstream calls |

| Plan | unavailable, unknown tenant | `plan_unavailable`; never another tenant's plan |

| Embedder | `None`, raises, wrong dimension | `rag_embedder_unavailable` |
| Adapter | any non-OK code | code propagated; no substitute, no empty result |
| Adapter | OK with `records is None` | `rag_retrieval_invalid` |

## Audit, trace and metrics

`emit_chat_audit(..., route="rag" | "vector", console=..., detail={"stage": last_stage, "code": refuse_code, "dropped": "n"})` is called in the `finally` of every handler, so refusals and sheds get records (Req 17.5). `detail` values are plain strings and counters only. The stage-scoped decision names the matched stage in `detail["stage"]` and in the `StageNote` trace (Req 6.6). `RequestHolds.note_input` records the query decision; `note_output` records the generator decision. `PerRequestExports` observations are called through the shared `chat.exports` (detector invocations, withheld). `FAIL_OPEN` stays pinned at 0. No tenant-derived metric label is added. New label-free counters, if any, are added to an existing producer and not to a new one; the implementer reuses `record_withheld` for withheld outputs.
