- LOAD 3-FAILURE-CLASS (item#29, P9): under sustained multi-tenant load, classify failures into THREE buckets with different owners/severities — do NOT lump them: (a) TRUE ISOLATION MIX = HTTP-200 with wrong REAL content and NO jsonrpc error → critical, must be 0; (b) TRANSIENT BACKPRESSURE = an id-matched JSON-RPC error (control's `-32000 "Internal server error."`) or 5xx that CLEARS on bounded client retry → graceful degradation, not a bug (echo/get-sum are idempotent so retry is safe; RETRIES=2 recovered 23/23 and 3/3); (c) EXHAUSTION/STORM = pids-cgroup breach, fd exhaustion, or a run of consecutive-503s → capacity failure. Measure (c) by reading the HOST cgroup `pids.current` (`/sys/fs/cgroup/system.slice/docker-<ID>.scope/pids.current`) — NO in-container fork, so it works even when a container is saturated (docker exec would itself fail to fork). Sandbox REUSE = container Id unchanged start→end; NO LEAK = pids.current drains back to baseline (~121) after load. Harness `scripts/mcp_load_live.py` (25×4/MCP=120-in-flight, 3000 calls). RESULT 3× GREEN: 3000/3000 each, effective_err=0, isolation_mix=0, 5xx=0, max_consecutive_503=0, peak_pids≤127/256, reuse+no-leak+limits all true. The control-plane `-32000` rate at high concurrency is the SATURATION BOUNDARY ceiling (Django policy plane), NOT a broker/sandbox/isolation defect. Evidence: mcp-parallel/findings/p9-29/LOAD.md.
- CONCURRENCY DUAL-ORACLE (item#28, P9): to prove "no dropped/mixed responses" when many tool calls hit ONE sandbox's stdio multiplexer (`_pending` dict keyed by JSON-RPC id) at once, stamp EACH request with TWO independent unique keys — the JSON-RPC `id` AND a unique nonce embedded in the echo `message` — and assert BOTH round-trip. id-match (resp.id==sent.id) catches a transport WAITER mix-up; nonce-match (our exact nonce in the reply text) catches a SERVER-SIDE content swap; id-match ALONE cannot catch a content swap, nonce ALONE cannot catch a waiter mix-up. Add get-sum(a,b) as a deterministic arithmetic oracle + a cross-tenant check (an org's reply must never carry another org's nonce). Harness: `scripts/mcp_concurrency_live.py` (CONCURRENCY in-flight PER MCP → 240/round across 15; PRE-WARMS each target first). RESULT: 3× consecutive GREEN, 1440/1440 each (drops=0,id_mm=0,content_mm=0,arith_mm=0,xtenant=0), p50~3.1–4.3s/p99~5.5–10s under 240-in-flight. GOTCHA: WITHOUT warmup, `content_mm` clusters in round 0 (a tools/call landing before `initialize` returns an id-matched 200 whose body is NOT the echo) while id_mm/drops stay 0 → that's a COLD-START/readiness property (item#29/B3), NOT a transport bug; warm all 15 before the graded burst. Evidence: mcp-parallel/findings/p9-28/CONCURRENCY.md.
- CONCURRENCY SATURATION BOUNDARY (iter21, P9.28→#29): "no dropped/mixed" (item#28) is NOT the same property as "no errors under load" (item#29). Under aggregate cross-org concurrency, the broker/sandbox **stdio id-demux and tenant isolation are perfect at every depth tested (60→240-wide): 0 dropped, 0 id_mismatch, 0 mixed, 0 cross_target.** What degrades is application-level ERRORS: at ≥180 simultaneous calls a fraction return HTTP 200 + JSON-RPC `-32000` whose message is control's `"Tool is not registered for this server"` (403 `tool_not_registered`, `control/.../mcp_connector/views.py:1076`) or DRF `"Internal server error."` (500, `main_app/exception_handlers.py`), forwarded verbatim by gateway `mcp_proxy.py:2540`. A single server at 60-deep is 100% clean → the ceiling is the **control(Django)+gateway policy plane** (DB/worker pressure), NOT the Cursor-owned broker/agent/docker_manager. When grading #28, classify an errored-but-correct-id response as `errored_under_load` (a #29 reliability signal), NOT as `mixed`/`dropped` (an error body has the right id and no result → provably not a mix or a drop). `scripts/mcp_multi_org_harness.py` env `CONCURRENCY_STRICT_ERRORS=1` gates on errored for the #29 load gate.
- NPROC/UID TRAP (iter20, P8.26): NEVER use an `nproc` ulimit for per-sandbox process caps. `RLIMIT_NPROC` is enforced by the kernel PER HOST-UID (counts tasks/threads across ALL containers), and every org sandbox runs as the SAME `sandbox` uid 1000 → an nproc ulimit becomes ONE budget SHARED across all tenants (breaks multi-org scaling: ~7/15 stdio servers fail to fork with EAGAIN "resource temporarily unavailable" → gateway shows 0-tools; AND lets one org fork-DoS the others). Use `pids_limit` (pids cgroup controller) — it IS container-scoped. Diagnosis tells: `docker top` shows few PROCESSES but cgroup `pids.current` (tasks/threads) is high; `id sandbox`=uid1000; host `ps -eLo uid | awk '$1==1000' | wc -l` ≈ sum of sandbox cgroup pids.current near the ulimit. Fixed in `docker_manager._sandbox_ulimits` (nofile only). Multi-org harness = `scripts/mcp_multi_org_harness.py` (must PRE-WARM all 15 before graded phases — MCP_CONCURRENT_INITS cap serializes cold npx starts).
